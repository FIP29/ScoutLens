# ScoutLens — Project Map

A file-by-file guide to the repository: what each file is for, and how it connects
to the rest of the system.

**78 tracked files** across five layers:

| Layer | Location | Role |
|---|---|---|
| Data source | `data/` | The raw FBref CSV the database is built from |
| Database | `db/schema/`, `db/logic/`, `db/seed/` | DDL, views/routines/triggers, and generated seed data |
| ETL | `etl/` | Converts the CSV into the database, and the database back into `.sql` |
| API | `server/` | Express REST layer over MySQL |
| Web client | `client/` | React scouting interface |
| Tooling & docs | `scripts/`, `docs/`, root | Launcher, smoke tests, documentation |

## How the layers connect

```
data/player_stats_2020_2026.csv
        │
        │  etl/import.js  (uses etl/parse.js for field cleaning)
        ▼
   MySQL: scoutlens ◄──── db/schema/*.sql   (tables, keys, indexes)
        │            ◄──── db/logic/*.sql    (views, rules, routines, triggers)
        │            ◄──── db/seed/*.sql     (alternative to the importer)
        │
        │  server/src/db/pool.js
        ▼
   server/src/routes/*  ──► HTTP :4000
        │
        │  client/src/lib/api.js  (Vite proxies /api → :4000)
        ▼
   client/src/pages/*   ──► browser :5173
```

`scripts/start.mjs` runs the API and the client together; `etl/run-sql.js` is what
applies any directory of `.sql` files.

## Root

### `package.json`
Root manifest and the project's command surface: `db:schema`, `db:import`,
`db:logic`, `db:setup`, `db:export`, `start`, `install:all`. Declares the three
dependencies the ETL needs (`mysql2`, `csv-parse`, `dotenv`).
Its scripts invoke `etl/*.js` and `scripts/start.mjs`; `install:all` recurses into
`server/` and `client/`.

### `package-lock.json`
Locks exact versions of the root (ETL) dependency tree so installs are reproducible.
Generated by npm from `package.json`; never edited by hand.

### `.env.example`
Template for local configuration — database host, port, user, password, name, and
the API port. Copied to `.env` during setup.
Read by `etl/config.js` and `server/src/db/pool.js`, which are the only two places
that touch environment variables.

### `.gitignore`
Keeps `node_modules/`, build output (`client/dist/`), the real `.env`, and editor
noise out of version control.
Its `.env` rule is what makes `.env.example` necessary.

### `README.md`
The front door: stack summary, feature list, prerequisites, step-by-step setup, the
pure-SQL loading route, project layout, an explanation of how filter selections
become parameterised SQL, data caveats, and a troubleshooting section.
Links out to the three files in `docs/`.

### `project-map.md`
This document.

## `data/` — source data

### `data/player_stats_2020_2026.csv`
The dataset the whole project is built from: 21,100 player-season rows × 85 columns,
scraped from FBref, covering the Big 5 European leagues 2020-21 → 2025-26. Vendored
from the upstream `FOOTBALL_FANTASY_ML` repository so the database can be rebuilt
without cloning it.
Read by `etl/import.js`; its path is resolved in `etl/config.js` and overridable via
`CSV_PATH`.

---

## `db/schema/` — table definitions

Applied first, in filename order, by `etl/run-sql.js`.

### `db/schema/01_schema.sql`
Creates the database and the core relational skeleton: `leagues`, `seasons`,
`nations`, `positions`, `teams`, `players`, the `player_seasons` fact table, and the
`player_season_positions` junction that resolves multi-valued positions into 1NF.
Must run before everything else; `players.born_key` (a generated column) is what
makes the `(name, birth year)` identity key work for players with an unknown birth year.

### `db/schema/02_stats.sql`
Creates the five statistic tables — `stats_standard`, `stats_shooting`,
`stats_keeper`, `stats_playing_time`, `stats_misc` — each a 1:1 optional extension of
`player_seasons` where the primary key is also the foreign key.
Depends on `01_schema.sql`; these are the tables `db/logic/01_views.sql` joins
together into one flat view.

### `db/schema/03_fantasy_app.sql`
Creates the fantasy scoring configuration (`fantasy_rulesets`,
`fantasy_scoring_rules`, `fantasy_points`) and the application tables (`users`,
`shortlists`, `shortlist_entries`, `squads`, `squad_players`, `saved_searches`).
The application tables are the read/write half of the app and are deliberately
untouched by the ETL, so a re-import never destroys a user's saved work.

## `db/logic/` — views, rules, routines, triggers

Applied after data is loaded, because several of these files read from populated tables.

### `db/logic/01_views.sql`
Defines `v_player_season` — the flat, fully-labelled join across all eight core
tables that nearly every API query reads from — and `v_fantasy_stat_facts`, which
unpivots scoring-relevant statistics into `(stat_key, value)` pairs.
`v_fantasy_stat_facts` is what makes the scoring formula data-driven: it is joined
against `fantasy_scoring_rules` by `sp_recalculate_fantasy_points`.

### `db/logic/02_fantasy_rules.sql`
Reference data: two named rulesets (`Classic`, `Attack Heavy`) and their 26 scoring
rules, expressed as points per unit of a stat, optionally scoped to a position.
Resolves position codes to ids by querying `positions`, so it must run after the
import. Changing scoring here plus a `CALL sp_recalculate_fantasy_points()` re-scores
the database with no application change.

### `db/logic/03_procedures.sql`
Defines `fn_active_ruleset()` and six procedures: `sp_recalculate_fantasy_points`,
`sp_player_trend`, `sp_compare_players`, `sp_leaderboard`, `sp_squad_projection`,
`sp_team_season_summary`.
Called from `server/src/routes/*` via `callProc()`; uses `DELIMITER` directives, which
is why `etl/sql-split.js` exists.

### `db/logic/04_triggers.sql`
Two triggers on `squad_players` enforcing the squad rules in the database: max 15
players, at most one captain, and every player from the squad's own season. Each
raises `SQLSTATE 45000` with a readable message.
`server/src/routes/scouting.js` catches these and maps them to HTTP 409, passing the
message through unchanged.

### `db/logic/05_analytics_views.sql`
Four aggregate views: `v_team_season`, `v_league_season`, `v_player_career`, and
`v_player_progression` (season-over-season deltas via `LAG()` window functions).
Read directly by `server/src/routes/analytics.js` and `players.js`, so the API never
aggregates in JavaScript.

### `db/logic/06_initialise.sql`
Final setup step: seeds the demo scout account (`users.user_id = 1`) and calls
`sp_recalculate_fantasy_points` for both rulesets so the app has scores on first load.
Depends on every other file in `db/logic/`; the demo user id is the one hard-coded as
`DEMO_USER` in `server/src/routes/scouting.js`.

## `db/seed/` — generated seed data

Plain `INSERT` statements produced by `etl/export-seed.js`. Together they are an
alternative to running the Node importer, letting the database be rebuilt from SQL
alone — useful from MySQL Workbench. Files are numbered so parents load before
children. **None of these should be edited by hand.**

| File | Contents |
|---|---|
| `db/seed/01_positions.sql` | The 4 position rows (GK/DF/MF/FW) |
| `db/seed/02_seasons.sql` | The 6 seasons, 2020-21 → 2025-26 |
| `db/seed/03_leagues.sql` | The 5 Big-5 competitions |
| `db/seed/04_nations.sql` | 138 nationalities |
| `db/seed/05_teams.sql` | 137 clubs |
| `db/seed/06_players.sql` | 8,225 distinct player identities |
| `db/seed/07_player_seasons.sql` | 21,100 fact rows — the core table |
| `db/seed/08_player_season_positions.sql` | 25,391 position links |
| `db/seed/09_stats_standard.sql` | 17,149 appearance/goal/card rows |
| `db/seed/10_stats_shooting.sql` | 17,149 shooting rows |
| `db/seed/11_stats_keeper.sql` | 1,233 goalkeeper rows |
| `db/seed/12_stats_playing_time.sql` | 21,100 rotation/team-success rows |
| `db/seed/13_stats_misc.sql` | 17,149 discipline/defensive rows |
| `db/seed/14_fantasy_rulesets.sql` | The 2 rulesets |
| `db/seed/15_fantasy_scoring_rules.sql` | The 26 scoring rules |

## `etl/` — data pipeline

### `etl/config.js`
Single source of configuration for every ETL script: loads `.env`, exposes the
resolved project `ROOT`, the `dbConfig` connection object, and `CSV_PATH`.
Imported by `import.js`, `run-sql.js` and `export-seed.js`.

### `etl/parse.js`
Field-level cleaning for the messy source CSV. Exports `coalesce`, `toInt`,
`toFloat`, `toUInt`, `parseAge`, `parseNation`, `parseLeague`, `parsePositions`,
`parseSeason`, `normalizeName` and `preferredSpelling`.
Pure functions with no dependencies, consumed only by `import.js`. Three of the
project's data-quality fixes live here: coalescing across `_playing_time` column
variants, splitting the two age formats, and folding accented names the way MySQL's
collation folds them.

### `etl/import.js`
The one-time CSV → MySQL loader. Truncates the statistics tables, collects distinct
dimension values in one pass, inserts players under a `(name, birth year)` identity,
then writes the fact rows and each stat category in batches, reporting counts.
Reads `config.js` and `parse.js`; writes to tables from `db/schema/`. Idempotent, and
never touches the application tables.

### `etl/sql-split.js`
Splits a `.sql` script into individual statements while honouring `DELIMITER`
directives, tracking quoting and comment state so a delimiter inside a string is
never mistaken for syntax.
Exists because `DELIMITER` is a *client* directive the MySQL server does not
understand — this lets the same files run both through `run-sql.js` and by hand in
MySQL Workbench. Used only by `run-sql.js`.

### `etl/run-sql.js`
Runs every `.sql` file in a directory, in filename order, statement by statement.
Powers `db:schema`, `db:logic`, and loading `db/seed/`.
Uses `sql-split.js` to split and `config.js` to connect. Detects the MySQL 8
"SUPER privilege and binary logging" failure and prints the fix, since MySQL's own
message states the problem but not the remedy.

### `etl/export-seed.js`
Dumps the loaded database back out as the plain `INSERT` files in `db/seed/`,
skipping generated columns and batching rows per statement.
The inverse of `import.js`; its output is consumed by `run-sql.js`.

## `server/` — REST API

### `server/package.json`
Manifest for the API: `express`, `cors`, `mysql2`, `dotenv`, with `start` and a
`--watch` `dev` script.
Installed by the root `install:all`.

### `server/package-lock.json`
Locked dependency tree for the API. Generated; not hand-edited.

### `server/src/index.js`
Application bootstrap: creates the Express app, enables CORS and JSON parsing,
exposes `/api/health` (which reports whether MySQL is reachable), mounts the four
routers, and defines the 404 and central error handlers.
Imports `db/pool.js` first so the project-root `.env` is loaded before anything reads
`process.env`. Mounts: `/api/meta` → meta, `/api/players` → players, `/api` →
analytics and scouting.

### `server/src/db/pool.js`
Creates the shared `mysql2` connection pool and exports `query()` for parameterised
statements and `callProc()` for stored procedures. Resolves `.env` from the project
root so the API, the ETL and MySQL Workbench all describe one database.
Imported by every route module; `decimalNumbers: true` means the client receives
numbers rather than strings for charting.

### `server/src/lib/http.js`
Small shared helpers: `asyncHandler` (routes a rejected promise to Express's error
handler), the `ApiError` class carrying an HTTP status, and `optionalInt` /
`requiredInt` for validating numeric parameters.
Used by all four route modules and by `filters.js`.

### `server/src/lib/filters.js`
**The security-critical module.** Translates filter selections into a parameterised
`WHERE` clause. Exports `FILTER_FIELDS` (the whitelist of 21 filterable fields and
their allowed operators), `SORT_FIELDS`, `buildWhere`, `buildOrderBy` and
`filtersFromQuery`.
Field names are *looked up* in the whitelist rather than concatenated, so only
resolved column names reach the SQL string and every value travels as a `?`
placeholder. Consumed by `routes/players.js`; also published through `routes/meta.js`
so the React filter builder renders from the same grammar.

### `server/src/routes/meta.js`
Serves the reference data every dropdown needs — seasons, leagues, positions,
nations, rulesets, row counts — plus the filter grammar itself, and a `/meta/teams`
endpoint narrowed by season or league.
Publishing `FILTER_FIELDS` here is what stops the client keeping a second copy of the
whitelist.

### `server/src/routes/players.js`
Player search (both a `POST` structured form and a `GET` query-string shorthand),
typeahead suggestions, the career profile, and single player-season detail.
Builds its SQL through `filters.js`, reads `v_player_season` and `v_player_career`,
and calls `sp_player_trend`. Counts and pages in two round trips rather than using
the deprecated `SQL_CALC_FOUND_ROWS`.

### `server/src/routes/analytics.js`
Head-to-head comparison, the fantasy leaderboard, league and club dashboards, and
ruleset listing/activation (which re-scores all 21,100 rows).
Mostly a thin wrapper over `sp_compare_players`, `sp_leaderboard`,
`sp_team_season_summary`, `sp_recalculate_fantasy_points` and the analytics views.

### `server/src/routes/scouting.js`
The write side: CRUD for shortlists and their entries, squads and their players, and
saved searches. Scoped to the seeded demo user (`DEMO_USER = 1`).
Translates database errors into meaningful HTTP responses — `SQLSTATE 45000` from the
squad triggers becomes a 409 carrying the trigger's own message, duplicate keys become
409, missing foreign keys become 404.

## `client/` — React interface

### `client/package.json`
Manifest for the web app: `react`, `react-dom`, `react-router-dom`, `recharts`, with
Vite and the React plugin as dev dependencies.

### `client/package-lock.json`
Locked dependency tree for the client. Generated; not hand-edited.

### `client/vite.config.js`
Vite configuration: the React plugin, port 5173, and a proxy sending `/api` to
`http://localhost:4000`.
That proxy is why the browser sees one origin and no CORS handling is needed in
development.

### `client/index.html`
The HTML shell Vite serves — page title, favicon link, the `#root` mount node, and
the module script that loads `src/main.jsx`.

### `client/public/favicon.svg`
The browser-tab icon: a small green ring mark on the app's dark background.

### `client/src/main.jsx`
Entry point: mounts `App` into `#root` inside `BrowserRouter` and `StrictMode`, and
imports the global stylesheet.

### `client/src/App.jsx`
The application shell — sidebar branding, the seven-item navigation, and the route
table mapping each path to a page component. Wraps everything in `MetaProvider`.

### `client/src/styles.css`
The entire visual design in plain CSS: custom-property palette, layout, panels, stat
tiles, forms, tables, chips, messages, the filter-builder grid, and the mobile
breakpoint. No framework, so the stylesheet is readable end to end.

### `client/src/lib/api.js`
Thin `fetch` wrapper exporting a single `api` object with one method per endpoint.
Centralises the `/api` prefix, JSON headers, 204 handling, and error unwrapping.
Imported by every page and by `MetaContext.jsx`; it is the only file that knows
endpoint URLs.

### `client/src/lib/format.js`
Display helpers: `num`, `int`, the `flag` emoji converter, and the shared
`POSITION_COLOURS` map.
Used by `Bits.jsx`, `ResultsTable.jsx` and most pages so "no data" renders as a
consistent dash everywhere.

### `client/src/lib/MetaContext.jsx`
Fetches the reference data once on mount and shares it through React context,
exporting `MetaProvider` and the `useMeta` hook.
Means every dropdown in the app is populated from the database rather than from
hard-coded lists. Consumed by `FilterBuilder`, `SearchPage`, `DashboardPage`,
`LeaderboardPage` and `SquadPage`.

### `client/src/components/Bits.jsx`
Small shared presentational pieces: `PositionChip`, `PlayerLink`, `Stat`, `Message`,
`Loading` and `Num`.
Imported by nearly every page; depends on `format.js` and `react-router-dom`.

### `client/src/components/FilterBuilder.jsx`
The scouting filter form. Renders a row per criterion — field, operator, value — with
dropdowns for fields whose values come from reference data, and free inputs otherwise.
Builds itself entirely from the filter grammar in `useMeta()`, so it cannot offer a
filter the API would reject, and a new backend filter appears here automatically.

### `client/src/components/ResultsTable.jsx`
The sortable results grid: fifteen columns, clickable sort headers with direction
arrows, and an optional per-row action button.
Used by `SearchPage`; the action slot is what adds a player to a shortlist.

### `client/src/pages/DashboardPage.jsx`
Landing view: database scale tiles, goals per league per season, average squad age
trends, and a latest-season league table.
Reads totals from `useMeta()` and aggregates from `api.leagues()`, pivoting league
rows into per-season records for the grouped charts.

### `client/src/pages/SearchPage.jsx`
The main scouting screen. Owns the filter state, runs searches, handles sorting and
paging, and pushes results onto a shortlist.
Composes `FilterBuilder` and `ResultsTable`; drops blank criteria before calling the
API so a half-filled row never reaches the server.

### `client/src/pages/PlayerPage.jsx`
Career profile for one player: headline totals, an output-by-season line chart, a
minutes-versus-points bar chart on dual axes, and the full season table.
Keeper profiles swap the second chart for clean sheets and saves. All data comes from
`api.player()`, which is backed by `sp_player_trend`.

### `client/src/pages/ComparePage.jsx`
Head-to-head comparison. Two independent player pickers (search → pick player → pick
season) feeding a per-90 radar and a side-by-side metric table with the better value
highlighted.
Calls `api.suggest()` then `api.search()` to resolve season ids, and `api.compare()`
for the comparison itself.

### `client/src/pages/LeaderboardPage.jsx`
Fantasy leaderboard with season, league, position, minimum-minutes and row-count
filters, plus ruleset switching. Shows the attack/defence/discipline points breakdown.
Activating a ruleset triggers a full re-score in MySQL and reloads the board.

### `client/src/pages/ShortlistPage.jsx`
Shortlist management: create lists, browse their entries joined to current stats,
and remove players or whole lists.
Players are added from `SearchPage`; this page is where they are reviewed.

### `client/src/pages/SquadPage.jsx`
Fantasy squad builder: create a squad for a season, search that season's players, add
them to a slot, optionally name a captain, and see projected points.
Deliberately restricts candidate search to the squad's own season to match the
database trigger, and surfaces trigger rejections verbatim when a rule is broken.

## `scripts/` — tooling

### `scripts/start.mjs`
Runs the API and the web client together in one terminal, prefixing each server's
output and shutting both down on Ctrl+C.
Spawns them as direct `node` processes rather than through `npm run`, because an
`npm` wrapper does not forward the signal to its child — which would leak both
servers with their ports still bound. Checks that dependencies are installed and says
so plainly if not.

### `scripts/smoke-test.mjs`
End-to-end API check: 24 assertions across every route group, including the injection
rejections, the trigger violations, and the captain-doubling projection. Cleans up
the rows it creates and exits non-zero on the first failure.
Depends only on a running API; the fastest way to confirm the whole stack works.

## Reading order for someone new

1. `README.md` — what it is and how to run it
2. `db/schema/01_schema.sql` — the data model everything rests on
3. `etl/parse.js` and `etl/import.js` — how messy CSV becomes clean rows
4. `db/logic/01_views.sql` — the one view the API reads
5. `server/src/lib/filters.js` — how a form becomes safe SQL
6. `client/src/components/FilterBuilder.jsx` — how that grammar becomes a UI
